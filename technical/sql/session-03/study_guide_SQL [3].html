01

مقدمة: الـ View يعني إيه؟

الـ View هو "جدول منطقي" (logical table) مبني على جدول حقيقي أو View تاني — لكنه مالوش بيانات خاصة بيه أبدًا. فكّر فيه كإنه "شباك" (window) بتشوف من خلاله بيانات جداول تانية، أو تعدّلها.

▸ فكّر فيها كده
الجدول الحقيقي (employee)
        |
        | (View = شباك بيطل عليه)
        v
Employee_D5  →  مش بيخزن بيانات
                بيعرض بس صفوف dno=5
                من جدول employee
المصطلحالمعنى
Viewجدول منطقي، مبني على جدول أو View تاني
Base Tableالجدول الحقيقي اللي الـ View مبني عليه
مخزّن إزاي؟كجملة SELECT بس داخل الـ data dictionary، مش كبيانات
أهم نقطة: لأن الـ View مالوش بيانات خاصة بيه، أي تعديل تعمله من خلاله (زي UPDATE أو INSERT) بيتوجّه فعليًا لجدوله الأساسي (base table) — مش بيتخزن في "مكان تاني".
02

مميزات استخدام الـ Views

مش بس "شكل تاني" للجدول — الـ Views بتحل مشاكل حقيقية في تصميم قواعد البيانات.

الميزةيعني إيه عمليًا
Restrict data accessتدّي مستخدم معيّن يشوف بس عمودين أو صفوف معينة، مش الجدول كله
Make complex queries easyتكتب JOIN وشروط معقّدة مرة واحدة جوه الـ View، وبعدين تستعلم منه بسهولة زي أي جدول عادي
Provide data independenceلو شكل الجدول الحقيقي اتغيّر، تقدر تعدّل الـ View بس من غير ما تكسر كل الاستعلامات اللي بتستخدمه
Present different views of the same dataنفس الجدول، يتعرض بأشكال مختلفة لأقسام مختلفة حسب احتياج كل واحد
03

Simple Views مقابل Complex Views

مش كل الـ Views زي بعض — الفرق ده بيحدد هل تقدر تعمل عليها UPDATE/INSERT/DELETE مباشرة ولا لأ.

الخاصيةSimple ViewComplex View
عدد الجداولواحد بسواحد أو أكتر (JOIN)
فيها دوال (functions)؟لأممكن (زي COUNT, SUM)
فيها تجميع بيانات (GROUP BY)؟لأممكن
عمليات DML من خلالها؟آه، غالبًامش دايمًا
ليه Complex View مش دايمًا تقبل DML؟ لو الـ View فيه GROUP BY أو دالة تجميعية زي COUNT(*)، مفيش معنى منطقي لـ "عدّل السطر ده" لإن السطر ده أصلاً ناتج حساب مش صف حقيقي من جدول واحد.
04

CREATE VIEW — إنشاء View

الصيغة العامة، ومثال حقيقي من الجلسة: View بيعرض بس الموظفين اللي قسمهم رقم 5.

syntax.sql
CREATE VIEW view [ (column1 [ , column2 ] ... ) ]
AS subquery
[ WITH CHECK OPTION ] ;
employee_d5.sql
CREATE VIEW Employee_D5
AS
select * from employee where dno = 5;

select * from Employee_D5;
لاحظ: بعد إنشاء الـ View، تقدر تستعلم عليه بـ SELECT زي أي جدول عادي بالظبط — مش هتلاقي فرق في شكل النتيجة، رغم إنه مش جدول حقيقي.
05

UPDATE و INSERT من خلال View

لأن Employee_D5 هو Simple View (جدول واحد، من غير دوال أو تجميع)، أي تعديل تعمله من خلاله بيتوجّه فعليًا لجدول employee الحقيقي.

update_via_view.sql
update Employee_D5
set fname = 'Ahmed'
where ssn = '333445555';
insert_via_view.sql
insert into Employee_D5 values (
'sara', 'A', 'English', '1212',
'1972-07-31', '5631 Rice, Houston, TX',
'f', 25000.00, '333445555', 5
);
مهم: الصف الجديد اللي اتضاف بـ INSERT فعليًا اتحط جوه جدول employee نفسه (مش جوه "الـ View")، وطالما قيمة dno بتاعته = 5، هيظهر تلقائيًا لو استعلمت على Employee_D5 تاني. الـ View بيعكس أي تغيير في الجدول الأساسي لحظيًا.
06

WITH CHECK OPTION — منع البيانات "الشاردة"

لو عملت View بشرط WHERE، إيه اللي يمنعك تضيف صف من خلاله ميحققش الشرط ده؟ هنا بالظبط دور WITH CHECK OPTION.

employee_d1.sql
CREATE VIEW Employee_D1
AS
select * from employee where dno = 1 with check option;
insert_ok.sql
-- dno = 1 → بيحقق شرط الـ View
insert into Employee_D1 values (
'aya', 'A', 'English', '1001', ...,
'333445555', 1
);
▸ Output
INSERT 0 1
(نجح — الصف بيحقق dno = 1)
insert_fails.sql
-- radwa عندها dno = 4، مش 1!
insert into Employee_D1 values (
'radwa', 'A', 'English', '1002', ...,
'333445555', 4
);
▸ Output المتوقّع
ERROR: new row violates check
option for view "employee_d1"

(اترفض! dno=4 مش بيحقق شرط dno=1)
خطر شائع جدًا: من غير WITH CHECK OPTION، الـ INSERT ده كان هينجح عادي (رغم إن الصف مش هيظهر بعد كده لو استعلمت على Employee_D1 تاني، لإنه مش بيحقق شرطها) — وده سلوك مربك. WITH CHECK OPTION بيمنع المشكلة دي من الأساس برفض أي INSERT أو UPDATE هيخرج بره حدود شرط الـ View.
07

تعديل وحذف Views

CREATE OR REPLACE VIEW بتخليك تغيّر تعريف View موجود من غير ما تحذفه وتعمله تاني، وDROP VIEW بتشيله بالكامل.

replace_view.sql
CREATE OR REPLACE VIEW vw_work_hrs
AS
SELECT Fname, Lname, Pname, Hours
FROM Employee, Project, Works_on
WHERE SSN = ESSN AND PNO = PNUMBER
      AND Dno = 5;
drop_view.sql
DROP VIEW Employee_D5;
لاحظ: DROP VIEW بتمسح تعريف الـ View بس (جملة الـ SELECT المخزّنة) — مش بتمسح أي بيانات من جدول employee الأصلي، لإن الـ View أصلاً مالوش بيانات خاصة بيه.
08

Complex View باستخدام Subqueries متعددة

مثال حقيقي من الجلسة: View اسمه reports بيحسب لكل قسم — عدد الموظفين، إجمالي ومتوسط الرواتب، عدد المشاريع، وإجمالي ساعات العمل، كل واحدة بـ subquery منفصلة.

reports_view.sql
CREATE VIEW reports
AS
SELECT
    d.dname,
    /* عدد الموظفين */
    (SELECT COUNT(*) FROM employee e
     WHERE e.dno = d.dnumber) AS employee_count,

    /* إجمالي الرواتب */
    (SELECT SUM(e.salary) FROM employee e
     WHERE e.dno = d.dnumber) AS total_salary,

    /* متوسط الرواتب */
    (SELECT AVG(e.salary) FROM employee e
     WHERE e.dno = d.dnumber) AS average_salary,

    /* عدد المشاريع */
    (SELECT COUNT(*) FROM project p
     WHERE p.dnum = d.dnumber) AS project_count,

    /* إجمالي ساعات المشاريع */
    (SELECT SUM(w.hours) FROM project p
     JOIN works_on w ON p.pnumber = w.pno
     WHERE p.dnum = d.dnumber) AS total_project_hours

FROM department d
ORDER BY total_salary DESC;
ليه ده Complex View؟ فيه أكتر من جدول (department, employee, project, works_on)، فيه دوال تجميعية (COUNT, SUM, AVG)، وناتجه أعمدة محسوبة مش نسخة مباشرة من صف حقيقي — فمينفعش تعمل عليه INSERT أو UPDATE مباشرة.
Correlated Subquery: كل subquery هنا بيستخدم d.dnumber من الاستعلام الخارجي جوّاه (WHERE e.dno = d.dnumber) — يعني بيتنفّذ من جديد لكل قسم لوحده. ده اسمه Correlated Subquery: الاستعلام الداخلي "مرتبط" بصف معيّن من الاستعلام الخارجي، عكس subquery عادي بيتنفّذ مرة واحدة بس.
09

الاستعلام على Complex View زي أي جدول

أهم فايدة عملية للـ View: بعد كل التعقيد اللي فوق، بقى تقدر تستعلم على reports بسهولة زي أي جدول عادي — كل الـ subqueries المعقدة اختفت وبقت "شغل جاهز" ورا الكواليس.

query_reports.sql
select * from reports;

select dname, employee_count
from reports
where employee_count > 0;
query_reports_full.sql
select dname, employee_count, total_salary,
       project_count
from reports
where employee_count > 0;
القيمة الحقيقية للـ View هنا: بدل ما تكرر كل الـ subqueries المعقدة دي كل مرة عايز تشوف تقرير الأقسام، كتبتها مرة واحدة جوه reports، وبقيت تستعلم عليها بجملة SELECT بسيطة زي أي جدول — ده بالظبط معنى "Make complex queries easy" اللي اتكلمنا عليه في الميزات.

قواعد البيانات على السحابة (Cloud Databases)

DBaaS (Database as a Service) بتديك وصول لموارد قاعدة بيانات كاملة على السحابة من غير ما تركّب أي هاردوير أو تنصّب أي سوفتوير بنفسك.

المحوريعني إيه
Ease of Use and Accessوصول عن طريق API، واجهة ويب، أو تطبيقات سحابية/عن بُعد
Scalability & Economicsتكبير أو تصغير التخزين والمعالجة وقت ما تحتاج، وتدفع على حسب استخدامك بس (Pay per use)
Disaster Recoveryنسخ احتياطية سحابية وتوزيع جغرافي يحمي بياناتك من فقدها

استرجاع صفوف من جدول حقيقي على Db2
